# perf-flow

输入一个网址,测量它的加载过程:**TTFB、HTML 收完、FCP、LCP**,标注 FCP / LCP 对应的页面元素,并支持自定义"某个元素何时出现 / 消失"的检测。操作都在本地网页界面里完成。

> 状态:v0.1,早期版本。`package.json` 里保留了 `private: true`,避免误发布到 npm;目前通过 GitHub 获取。

## 运行

需要 Node.js 20+ 和本机已安装的 Google Chrome。

```bash
npm install
npm start            # 启动本地服务并自动打开浏览器界面
```

演示页面(不依赖外部网站,带延迟的 CSS、流式 HTML、大图、接口请求和"遮罩消失"):

```bash
npm run demo         # http://127.0.0.1:9090/
```

在界面里输入 `http://127.0.0.1:9090/`,添加几项检测即可体验。

命令行选项:`--port <n>`、`--no-open`、`--home <dir>`。环境变量 `PERF_FLOW_CHROME` 可指定 Chrome 路径。结果保存在 `~/.perf-flow/`。

## 测量方式

- 每一轮使用**全新的浏览器上下文**(冷缓存),不限速。默认 3 轮,汇总取**中位数**并给出范围。
- 默认使用有窗口的 Chrome(有 GPU);可在界面勾选"无头模式"。
- 可选的"画面标注"会**额外多跑一轮**并录屏,用于在截图上框出元素。它不计入上面的统计。
- FCP / LCP / TTFB 来自浏览器的 Performance API。

### 自定义检测

| 类型 | 含义 | 精度 |
|---|---|---|
| CSS 选择器 · 出现 | 元素存在且可见(图片需加载完成) | 约 1 帧 |
| CSS 选择器 · 消失 | 曾经可见,之后不可见或被移除 | 约 1 帧 |
| 页面文字 | 可见文本中出现 / 消失(忽略 script / style) | 约 1 帧 |
| 网络请求 | 地址包含关键字(`re:` 开头为正则)的请求开始 / 完成 | 精确(Resource Timing) |
| JS 表达式 | 表达式为真(如 `window.appReady === true`) | 约 1 帧 |

"约 1 帧"指:条件在某一帧被观察到,取下一帧的起点作为"用户看到"的时间,存在几十毫秒以内的误差。

## 加载时间线:总览与聚焦

**总览**不分组,所有请求和时间点按时间顺序排成一列:条按开始时间,时间点(菱形)按发生时间。决定某个时间点的那条请求会带标签,写着“决定 FCP / 决定 DCL / 决定 LCP / 决定 load / 决定 TTFB”。**同一个资源只画一行**:比如一个同步脚本既是 FCP 的阻塞资源、又是 DCL 的决定者,标签会合并成“决定 FCP · 决定 DCL”,悬浮卡片里列出它的所有角色;它在每个相关的聚焦里都会出现。脚本**下载**和脚本**执行**是两行(执行那行带棕色的“执行”标签,放在文件名前面)。没有收起和展开,全部直接显示。

**总览里不显示“无法识别”的空白**:这类空白在一个真实页面上有好几段,全放进来会看不清。图例里会写明“这一轮有 N 段”,不会悄悄消失,要看它们请用聚焦。

**聚焦**(右上角的 `总览 | 服务端 | FCP | LCP | DOMContentLoaded | load | 我的检测`):只看到某个时间点为止、一路上的阻塞,包括“无法识别”的空白。你选了 FCP,就只显示 FCP 之前的:

- **FCP**:请求(DNS、连接、等待服务器响应、下载 HTML)→ 渲染阻塞资源 → 无法识别的空白 → FCP。
- **LCP**:FCP 的路径,再加上 LCP 元素自己的下载(图片或 CSS 背景图)、下载前后的空白、最终 LCP。
- **DOMContentLoaded**:请求 → 同步脚本 → HTML 解析完成 → `defer` / `module` 脚本 → DOMContentLoaded。
- **load**:DOMContentLoaded 之前的全部阻塞,加上 DOMContentLoaded 之后仍拖住 load 的请求。
- **服务端**:“等待服务器响应”这段时间里服务端做了什么(见下文“服务端明细”)。
- **我的检测**:你的检测的时间点。工具没有记录是什么在阻塞它们,所以只列出请求阶段和检测本身。

**聚焦里并行的只取阻塞的那一条**:比如有三个渲染阻塞的样式表同时下载,只显示结束最晚的那个,因为 FCP 要等的是它;其余的不在这里显示(总览里有)。但如果前一个请求结束后紧接着(25 ms 内)才发出下一个(样式表 `@import` 另一个样式表、服务端先调接口 A 再调接口 B),说明它们是串行的,前一个也算在路径上。**前后关系只能按时间推断**:浏览器的记录里没有“谁导致了谁”,所以这是按时间做的判断,界面上写的“决定 X”指的是“结束得最晚的那个”。

聚焦时,时间轴会缩到这条路径的范围。

## DOMContentLoaded 与 load 由什么决定

判断规则来自对 17 个构造页面的实测(每个页面只放一种东西),不是凭规范推断的:

| 在等什么 | 谁可能是决定者 |
|---|---|
| HTML 收完 → `domInteractive`(解析完成) | **同步脚本**(没有 `async` / `defer` / `module`);让后面脚本等待的阻塞样式表(只标为“可能”) |
| `domInteractive` → DOMContentLoaded | **`defer` / `module` 脚本** |
| DOMContentLoaded → load | 图片、样式表、字体、iframe、**`async` 脚本**、脚本注入的资源 |

另外:`fetch` / XHR / beacon **既不推迟 DOMContentLoaded,也不推迟 load**;屏幕外的懒加载图片不推迟 load。

**无法识别的部分画成带斜纹的横线**:资源下载完成之后的脚本执行、HTML 解析本身,Resource Timing 里没有记录。超过 150 ms 的空白会在聚焦的时间线上画成一条“无法识别”的斜纹横线,起止就是这段空白的起止,位置紧接在决定者之后(FCP 之前的空白画在 FCP 之前)。不会把剩下的时间归给别的东西。

**同步脚本会阻塞什么,取决于它在哪里、在做什么**(实测):

| 情形 | FCP | LCP |
|---|---|---|
| 同步脚本在 `<head>` | 被推迟到脚本结束 | 被推迟 |
| 同步脚本在 `<body>` 末尾(下载中) | 不受影响 | 不受影响 |
| 同步脚本在 `<body>` 中间(下载中) | 不受影响(脚本前的内容先画出) | 脚本**后面**的内容晚出现,可能推迟 LCP |
| 内联脚本占住主线程(无论在哪) | 一起被推迟(连前面的内容也画不出来) | 一起被推迟 |

**`load` 事件什么时候触发**:文档解析完成之后,在途的、会拖住 load 的子资源(图片、脚本、iframe 等)数量降到 0 的那一刻触发,**只触发一次**。触发之后再发的请求不影响它。所以:
- 每隔一段时间请求一张图,只要请求之间有空档,load 会在空档里触发;之后的请求不再影响。
- 一连串首尾相接的图片、或互相重叠的请求,**load 可以一直不触发**。fetch / XHR 不会拖住 load。
- load 不触发时,这一轮**不会失败**:FCP、LCP、DCL、自定义检测照常测量,load 记为“未触发”,并列出观察结束时**仍未完成的请求**。汇总里如果只有部分轮次触发,会明说“只有 x/y 轮触发”,时间只来自触发了的那几轮。

**没有验证的**:`<video>` / `<audio>` / `<link rel=preload>` 等类型会不会拖住 load。这类请求会被单独注明“工具无法确认”,不参与决定者的判断。

DOMContentLoaded 和 load 的数值取**事件触发的时刻**;事件处理函数的耗时在悬浮卡片里单独显示。旧版本记录取的是事件结束的时刻,没有请求明细,界面会标明。

## 查看范围:汇总或单轮

结果区有一个固定在顶部的“查看范围”工具栏,同时控制卡片、加载时间线和元素表:

| 选择 | 卡片 | 加载时间线 | 元素表 |
|---|---|---|---|
| **汇总** | 参与统计各轮的**中位数**(可切换为**平均值**)和范围 | **合成的汇总时间线**:每一行(各阶段起止、FCP、LCP、自定义检测、DOMContentLoaded、load)分别取各轮的中位数或平均值 | 按元素归并,标出每个元素出现在几轮里 |
| **第 N 轮** | 这一轮的实际值,并标出比汇总中位数快 / 慢多少 | 这一轮的实际时间线 | 这一轮自己的候选 |

- **汇总时间线是合成的,不是某一次真实的加载**:各行的数值来自不同的轮次,可能出现在真实加载中不会有的先后关系。想看真实的一次,请选某一轮。合成后的 TTFB / FCP / LCP / 各检测的数值与卡片完全一致(已用全部历史记录对照)。
- 汇总的 LCP 行:最终元素取各轮中出现次数最多的那个,时间取各轮最终 LCP 时间的统计值;只在个别轮出现的候选元素会单独列出,并标注“x/y 轮”。
- 汇总时可以取消勾选某一轮的“参与统计”(例如首轮受 DNS / 连接冷启动影响)。数据仍然保留,随时可以恢复;至少保留一轮。排除只在当前界面有效,不会修改已保存的结果文件。
- 默认用中位数:平均值容易被偶发的慢轮次拉高。悬浮卡片里始终同时给出两者。
- **参考画面不随范围变化。** 画面来自单独的一轮录屏(为了避免录屏影响常规轮的耗时),只有这一轮有画面。元素表随范围变化;点击表格里的一行,会在参考录屏里找到同一个元素并画框,参考录屏里没有这个元素时会明确提示。
- 结果顶部的提醒标签始终按汇总计算,不受单轮视图影响。

## 结果页顶部的提醒

结果顶部会汇总需要注意的问题,悬停看明细,部分可点击跳转:

| 提醒 | 触发条件 |
|---|---|
| 只有 N 轮有效,中位数不可靠 | 有效轮数少于 3 |
| 第 N 轮明显偏慢 | 样本不少于 3 轮时,某轮的 TTFB / FCP / LCP 超过中位数 1.5 倍且至少多 150 ms |
| 最终的 LCP 元素被遮挡 | 至少一半的有效轮里,最终 LCP 元素被其他元素盖住 |
| LCP / FCP 元素在各轮间不一致 | 各轮的元素不是同一个,此时各轮的时间不可直接比较 |
| 检测没有命中 / 只在部分轮命中 | 自定义检测的条件在超时前不成立 |
| 测量失败 / 页面发生了跳转 | |

## 服务端明细

浏览器只能看到"等待服务器响应"这一整段。要知道服务端在这段时间里做了什么,有两种方式,时间线里“等待服务器响应”下面会长出分支(也可以用右上角的“服务端”聚焦单独看):

**1. 读取 Server-Timing(不需要任何设置)**:如果服务端自己在响应头里输出了 `Server-Timing`,工具会自动读出来,线上页面也适用。这个头只有名称和时长,**没有起点**,所以只能列出来,不能画在时间轴上,界面会这样标明。

**2. 分析本机 Node 服务(表单里勾选“分析服务端”)**:输入本机地址(例如 `http://localhost:8081`)并勾选,**不需要改你的代码,也不需要重启服务**。工具会:

1. 按端口找到监听它的进程,确认它是**同一用户的 Node 进程**(其他程序不会被碰,发信号前先核对);
2. 给它发 `SIGUSR1`,让 Node 临时打开调试端口(`127.0.0.1:9229`);如果你自己已经用 `--inspect` 开着,就直接用,测完也不会去关;
3. 核对调试端口对面确实是这个进程后,注入一段**只读探针**(`src/server-probe.js`,订阅 Node 内置的 `diagnostics_channel`),记录页面请求在服务端的耗时,以及它发出的上游调用(`http` / `https` 模块和原生 `fetch`);
4. 每轮测量前后清空、取回数据,全部测完后卸载探针、关闭调试端口。探针在被测进程里还设了 15 分钟的自动撤销,防止 perf-flow 异常退出时残留。

探针只记录:方法、路径(不含查询参数)、第一个字节写出的时刻、状态码,以及上游调用的目标、起止和状态。**不记录**请求头(只读取判断“是否页面导航”所需的 `sec-fetch-dest` 和 `accept`)、cookie、请求体。

时间线上,服务端的内容直接**缩进在“等待服务器响应”下面**(服务端处理的时间就是这一段,所以不另列一行):

- 缩进的行是这段时间里服务端发出的**上游调用**,按开始时间排列;时间重叠就是并行,首尾相接就是串行;响应写出之前最后结束的标为**决定 TTFB**。聚焦“服务端”时只显示全部调用;聚焦其他时间点时,只显示它和串行在它前面的调用,并行的其他调用在总览里。
- 没有被任何调用覆盖、超过 10 ms 的空白画成**无法识别**(阈值取得很小,是为了让这些行能和“等待服务器响应”对上账;只在聚焦里显示):可能是服务端自己的同步计算、数据库或 Redis 等探针不覆盖的调用、事件循环被其他请求占着,工具不会猜。
- 服务端通过 `Server-Timing` 上报的阶段也列在这里,只显示时长。
- **加起来是否等于等待时间?** 看单轮:上游调用实际占用(并行的只算一次,所以调用时长直接相加可能更大)+ 服务端自己 / 无法识别 + 网络往返 = 等待时间,悬浮卡片里逐项列出。**汇总视图里每一项是各轮分别取的中位数,中位数不能相加**,所以汇总里这几项加起来会和等待时间有些出入。

**浏览器和服务端的时钟不是同一个**,工具用“浏览器看到的整个等待,减去服务端自己用掉的时间,剩下的是网络往返,去程和回程各占一半”来把服务端的起点放到页面时间线上。悬浮卡片里会写出这个往返估算值;本机访问时通常只有几毫秒。如果服务端记录的时间比浏览器看到的整个等待还长,说明匹配到了别的请求,这一轮的服务端数据不会被采用。

**限制**(都会在界面里明说,不会悄悄略过):

- 只支持 **Node 18 及以上**,且服务**必须在本机**由**同一用户**运行(Docker 里、远程开发机上的不行)。其他语言的服务请输出 `Server-Timing`。
- 看不到数据库、Redis、消息队列等调用,也看不到服务端自己的 CPU 计算,这些会显示为“无法识别”。
- 如果服务自己处理了 `SIGUSR1`(例如用它来重载配置),或用 `--disable-sigusr1` 启动,不能使用这个功能。
- 调试端口 `9229` 被另一个进程占着时不会附加,界面会说明。
- 测量期间服务被重启(例如 nodemon 热重启),探针会丢失,界面会提示。
- 调试端口打开的那段时间里,本机其他进程也可以连上它,所以这个功能需要你主动勾选,并且测完立刻关闭。
- 集群模式下,监听端口的进程不一定是处理请求的进程,匹配不到时界面会如实说明。

已在 Node 18、20、22、24 上,用 CommonJS 和 ES Module 两种写法的演示服务验证过。想先体验,可以运行 `npm run demo:server` 启动 `examples/upstream-demo.cjs`,再在界面里输入 `http://127.0.0.1:9494/page` 并勾选“分析服务端”。真实业务框架(Koa、Express、Next.js 等)和反向代理场景尚未验证。

## 数据从哪里来、能识别什么、不能识别什么

所有数值都来自 Chrome 自己报告的标准接口,工具不做估算:

| 数据 | 来源 | 说明 |
|---|---|---|
| TTFB、HTML 收完、DNS、连接、domInteractive、DOMContentLoaded、load | `PerformanceNavigationTiming` | 毫秒级,准确 |
| 每个请求的下载起止、`<script>` 的 async / defer 属性 | Resource Timing + DOM | 下载时间准确;脚本执行耗时没有记录 |
| FP / FCP | `PerformanceObserver`(`paint`) | 准确 |
| LCP 及候选元素 | `PerformanceObserver`(`largest-contentful-paint`) | 时间取渲染时间;跨域图片没有 `Timing-Allow-Origin` 时浏览器只能给出加载完成时间,工具会标出“时间来源”并提醒 |
| 渲染阻塞资源 | Resource Timing 的 `renderBlockingStatus`(Chrome 的标记) | 见下 |
| 网络请求类检测 | Resource Timing | 精确 |
| 选择器 / 文字 / JS 表达式类检测 | 工具自己的观察逻辑(MutationObserver + 逐帧检查) | 约 1 帧的误差 |
| LCP 是否被遮挡 | 工具自己的判断(`elementFromPoint` 采样) | 启发式,可能判断不准 |
| 脚本执行(来源、起点、耗时) | `PerformanceObserver`(`long-animation-frame`,Chrome 123+) | 只含所在帧长于 50 ms、自身执行不少于 5 ms 的脚本;**脚本在页面第一次绘制之前执行时,Chrome 不一定会报告**,见下 |
| 参考画面 | CDP 录屏 | 与页面时间线属于两个时钟,约差一两帧 |
| 服务端阶段(Server-Timing) | `PerformanceNavigationTiming.serverTiming` | 服务端自己上报,只有时长没有起点 |
| 服务端处理与上游调用 | 注入本机 Node 进程的探针(`diagnostics_channel`) | 只限本机 Node;与浏览器的对齐是估算,见上 |

**渲染阻塞资源**:只显示被 Chrome 标记为渲染阻塞的**网络请求**,包括 `<head>` 里的样式表、同步脚本、`@import` 引入的样式表。已用构造页面验证:`async` / `defer` / `module` 脚本、`media` 不匹配的样式表不会被误标。

**脚本执行**:Resource Timing 只记到脚本**下载完成**,下载完之后"排队等前面的脚本、真正执行"这一段没有记录,以前只能标成"无法识别"。现在用 Chrome 的长动画帧接口把其中的一部分识别出来,在时间线上画成棕色的"执行 xxx.js",并从"无法识别"里扣掉。比如一个同步脚本 3 ms 就下载完了,却要执行 120 ms,这 120 ms 现在能看到。它有三个限制,都会写在悬浮卡片里:
- 只记录**所在帧长于 50 ms、自身执行不少于 5 ms** 的脚本,更短的看不到。
- **脚本在页面第一次绘制之前执行时,Chrome 不一定会报告**。实测:同一个页面、同一个 700 ms 的脚本,8 次加载只有 1 次被报告;而同样的脚本放在第一次绘制之后,6/6 次都报告。所以“FCP 之前的脚本执行”可能漏掉,这时那一段仍然显示为"无法识别"。没有这条记录,不代表没有执行。
- 需要 Chrome 123 及以上;旧版本和旧记录没有这项数据。

**以下情况工具仍然无法识别**,发生时界面会明说,不会写成“没有阻塞”:
- 上面没覆盖到的脚本执行(更短的、或没被 Chrome 报告的)、内联样式
- 还在等待下载的同步脚本:同步脚本会让解析器停下来,等它下载完并执行完才继续,而它不是 Chrome 标记的"渲染阻塞资源",所以这段等待现在也落在"无法识别"里
- 样式计算与布局
- 字体加载(我的构造没有复现字体拖慢首屏,所以不能下结论)
- 主线程繁忙

当最后一个阻塞资源结束(或没有阻塞资源时 HTML 收完)到 FCP 之间超过 150 ms,界面会提示“这段时间无法识别原因”。

**测量环境**:每轮全新浏览器上下文(冷 HTTP 缓存),不限速,在本机本网络下测量;操作系统的 DNS 缓存、CDN 和服务端缓存不会被清除,所以第一轮往往更慢。数值代表“这台机器上的这次测量”,不代表真实用户的体验。Chrome 会自动更新,跨日期对比时请留意头部显示的 Chrome 版本。

## 已知限制

- **FCP 对应的元素是推断值。** 浏览器不提供这个信息,这里取与 FCP 同一时刻(±25 ms)出现的最早 LCP 候选。
- **LCP 元素可能不稳定**,也可能被其他元素遮住(例如不透明的加载遮罩),这时画面上看不到它,但浏览器仍计为 LCP。工具会检测并提示:对元素可见区域取 5 个点调用 `elementFromPoint`,至少 3 个点的最上层元素不是它自己(或后代)就判定为被遮挡。`pointer-events: none` 的覆盖层、半透明遮罩可能判断不准。
- 画面标注来自单独的一轮录屏,与统计用的轮次不是同一次加载;录屏可能影响耗时。
- 目前没有网络 / CPU 限速。
- 脚本执行的识别依赖 Chrome 的长动画帧接口,有上面写的几条限制;想拿到完整的主线程活动,需要 Chrome 的性能 trace(能看到每个任务和脚本的执行耗时),目前没有集成。
- 服务端明细只在本机 Node 服务上可用,且没有 CPU 采样,见上文“服务端明细”。
- 目前只在 macOS + Chrome 上验证过;Windows / Linux 的 Chrome 自动查找依赖 Playwright 的 `channel: 'chrome'`,未测试。

## 安全

服务只监听 `127.0.0.1`,校验 `Host` 头(防 DNS 重绑定),写操作要求同源并带自定义请求头(防其他网页向本机发请求)。只接受 `http` / `https` 网址。界面中来自被测页面的文字一律以纯文本渲染。

“分析服务端”会向本机进程发送信号并注入代码,所以限制得很死:只接受解析到本机的地址;发信号前先确认目标是**同一用户的 Node 进程**(对其他程序,`SIGUSR1` 的默认动作是终止它,所以不会发);注入前核对调试端口对面确实是该进程;界面不提供启动任何命令的入口。这个功能只能由同源页面带自定义请求头触发,不要把 perf-flow 的端口暴露到本机以外。

## 界面技术

界面使用 [Preact](https://preactjs.com/) 和 [htm](https://github.com/developit/htm),**没有构建步骤**:浏览器通过 import map 直接加载 `ui/vendor/` 下的单文件模块(附各自的许可证文本:Preact 为 MIT,htm 为 Apache-2.0)。

```
ui/
  index.html         入口(含 import map)
  main.js            应用与状态
  components/        Form / Summary(指标卡)/ Timeline(瀑布时间线)/ Shot(画面与元素表)/ Tooltip(悬浮卡片)
  lib/               格式化、数据模型、说明文字、接口调用
  vendor/            preact / hooks / htm
```

时间线是自己用 HTML 和 CSS 画的,没有使用图表库:行里混合了网络阶段、里程碑和自定义检测,现成的瀑布图库都是围绕请求设计的。
